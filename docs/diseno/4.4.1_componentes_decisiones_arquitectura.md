### 4.4.1 Componentes y decisiones de arquitectura

**Figura 9. Arquitectura general de la solución**

[Ver figura 9](figuras/figura_09.png)

> *Descripción (añadida):* diagrama de despliegue. Usuarios (Directivo, Coordinador, Tutor, Consultor, Administrador) entran por HTTPS al sistema CIUMB en PHP (front web, widget del chatbot, backend con sesión, roles y token de servicio), que llama por REST a la API interna no publicada a internet: POST /informes/personalizado, POST /informes, GET /semantica, GET /informes/{id}/descargar, GET /salud/ia.
> El contenedor Docker «Servicio de informes · Python 3.12 + FastAPI» agrupa intérprete del prompt (IA), validador de especificación, compilador (SQLAlchemy Core), motor estadístico, ML, gráficos, contrato (Pydantic + JSON Schema), orquestador de IA, validador de cifras, ensamblador/exportador y ETL nocturno (APScheduler). Datos: BD transaccional con usuario de solo lectura, esquemas ana_ y rpt_, volumen de archivos exportados.
> Salida a internet solo hacia proveedores gratuitos (Google AI Studio/Gemini, Groq, OpenRouter :free; servicio de IA UMB a futuro) con prompt depurado o contrato de solo agregados. Modo degradado RF-11: sin proveedor se entregan plantillas con texto de plantilla.

Fuente: Elaboración propia.

Usuarios. Entran al sistema del CIUMB desde el navegador, con su sesión y su rol del Módulo 7. El rol determina sobre qué datos puede pedir informes y qué plantillas base ve (RF-21). Un tutor solo ve las prácticas a su cargo, un coordinador su facultad y un directivo todo el centro.

Sistema CIUMB. Es la aplicación existente en PHP, con su front, su backend y su base de datos. El chatbot se integra como un componente más del front. El backend llama a la API del servicio de informes con un token de servicio y le pasa el rol y el alcance del usuario, de modo que el servicio no maneja contraseñas ni sesiones propias.

Servicio de informes. Es un contenedor Docker con Python y FastAPI, desplegado en el mismo servidor institucional (RNF-12). Expone una API REST interna, que no se publica a internet, con las rutas que define la sección 8.1 de los requerimientos, más GET /semantica, que publica la capa semántica para la capa de IA. Dentro del contenedor, cada componente es un módulo de Python con una interfaz definida, lo que permite probarlo por separado y cambiarlo sin afectar a los demás (RNF-08).

Datos. El servicio lee la base transaccional con un usuario de solo lectura, escribe el datawarehouse en el esquema ana_ y su propia configuración y trazabilidad en el esquema rpt_. Los archivos exportados y los gráficos se guardan en un volumen del contenedor que entra en el respaldo del servidor.

Proveedores de IA. La capa de IA de la práctica complementaria conecta el servicio con proveedores de capa gratuita compatibles con el formato de chat de OpenAI, en una cadena de respaldo configurable por variables de entorno (RF-07, RF-08). Las opciones que proponen los requerimientos son Google AI Studio, Groq y OpenRouter. Hacia ellos cruzan internet solo dos cosas. El prompt del usuario con la capa semántica publicada (nombres y descripciones, sin datos ni nombres de tablas), para obtener la especificación, y el paquete del contrato, con cifras agregadas. Antes de enviar el prompt, la capa de IA aplica la misma lista de patrones del contrato para retirar correos, documentos o NIT que el usuario haya escrito. Cuando la universidad tenga su propio servicio de IA, se agrega a la cadena cambiando la configuración.

La Tabla 18 registra las decisiones de arquitectura que tienen alternativas razonables. La Tabla 19 lista las tecnologías elegidas y su licencia, para demostrar el cumplimiento de la restricción de costo cero (RNF-01).

**Tabla 18. Registro resumido de decisiones de arquitectura**

| Id | Decisión | Alternativas consideradas | Razón y consecuencia |
|---|---|---|---|
| DA-01 | Datawarehouse como esquema ana_ en el servidor existente | Servidor aparte, nube gratuita, consulta directa | Costo cero y sin infraestructura nueva; se mitiga la carga con ETL nocturno (Tabla 14) |
| DA-02 | Servicio analítico en Python con FastAPI | Motor estadístico dentro del sistema en PHP | Python tiene las librerías estadísticas y de ML de referencia; obliga a mantener un servicio adicional, que se aísla en Docker |
| DA-03 | La IA traduce el prompt a una especificación y redacta; las cifras las calcula el software | Que la IA escriba el SQL (text-to-SQL); catálogo cerrado de informes | Abre el sistema a cualquier informe que la capa semántica pueda expresar, sin que la IA consulte ni calcule; lo que la capa no tenga se explica al usuario y se registra para ampliarla |
| DA-04 | Contrato de datos JSON versionado entre análisis e IA (versión 2.0.0) | Enviar tablas o texto libre al modelo | Permite validar esquema, anonimato y cifras; cambiar el contrato exige subir su versión |
| DA-05 | Validador determinista con plantilla de respaldo | Confiar en el modelo o pedirle autoverificación | Ninguna cifra sin verificar llega al usuario; algunos informes saldrán con texto de plantilla, más rígido |
| DA-06 | Modelado dimensional de Kimball | Modelo normalizado de Inmon | Entrega por procesos en cada sprint y consultas simples; algo de redundancia controlada |
| DA-07 | Capa semántica como única definición de lo que se puede pedir | Lista de informes en el código; mostrar a la IA el esquema físico | Agregar una métrica o dimensión es un registro que aprueba el administrador (RF-22), sin desplegar código; la IA nunca ve nombres de tablas |
| DA-08 | El tipo de gráfico lo define el prompt; si no lo indica, reglas de recomendación | Gráfico fijo por plantilla; que la IA elija el gráfico | Respeta lo que pide el usuario y es determinista cuando no lo pide; si el tipo pedido no es compatible, se usa el más cercano y se avisa (Tabla 21) |
| DA-09 | Plantillas base como especificaciones precargadas y opcionales | Plantillas como única vía de entrada; sin plantillas | Dan atajos para los informes frecuentes y sirven como pruebas de regresión sin limitar lo que se puede pedir |
